% Abstract
\begin{abstract}
Cache side-channel attacks such as Prime+Probe remain a significant threat in modern microarchitectures. While prior work primarily focuses on scalar memory accesses, the role of vector (SIMD) instructions in these attacks is not well understood. This paper evaluates how vector instructions (e.g., AVX) influence cache behavior, timing resolution, and the effectiveness of Prime+Probe attacks. To that aim, multiple PoC programs were created each with different levels of the attack in mind to explore vector instructions, how they interact with memory, and what different cache levels look like. During evaluation, it was found the the vpgather set of instructions can be used to detect memory access from different sets in the L1D cache. During evaluation, there were multiple findings that also lead to difficulties with this reading. First, apparent pipelining leading to subsequent Prime+Probe iterations on the same or different sets resulting in different timings. Second, micro-op optimization around vector instructions causing worse performance when isolated with lfence. Lastly, noise around scheduling and cache flushing causing major outliers (>1000\% baseline of 100+/-10).
\end{abstract}

\section{Introduction}
Cache side-channel attacks exploit shared microarchitectural resources to extract sensitive information. Prime+Probe is a widely studied technique that infers victim memory access patterns by observing cache eviction behavior. This behavior can give insight into which programs are executing and what data it's processing. Because this information is revealed at the hardware level, attackers can leverage these techniques to understand what other users are running on shared hardware in virtually isolated environments such as the cloud.

Most prior work assumes scalar memory accesses. However, modern CPUs heavily utilize vector instructions (e.g., AVX, SSE) for graphics, cryptography, and AI systems. This has created a shift in CPUs found in home PCs. Instructions like those in the AVX512 ISA extension are now becoming available on CPUs the average consumer buys. This allows developers and attackers to start using these instructions in the software that they make.

There hasn't been any research in using the capabilities of these instructions for memory access. This paper will look at a variety of techniques for using vector instructions to prime and probe the memory. The goal is to learn how different techniques interact with microarchitectural optimizations including the prefetcher, branch prediction, pipelining, and vector instruction pathways. It will also evaluate how vector instructions can increase timing resolutions to possibly support a Prime+Scope approach\cite{10.1145/3460120.3484816} that probes in parallel with the victim program's execution.

\section{Background}

\subsection{Cache Architecture}
Modern CPUs employ multi-level cache hierarchies (L1, L2, L3). L1 is the fastest and smallest. It has a separate cache for instructions (L1I) and the data (L1D) those instructions act on. This makes it useful for short loops and commonly references data. L2 is slightly larger and slower. It stores both instructions and data together. Every core has an L1D, L1I, and L2 cache to itself. When a program can't find its instruction or data in the L1 or L2 caches, it falls back to the largest and slowest cache: L3 or Last Level Cache (LLC). L3 is shared across all cores and it the last place to look on the CPU before defaulting to of-chip memory and storage.

Caches are structured with lines and sets. A line is typically 64 bytes, and the caches associativity will determine how many lines are in a set. For example, an 8-way associative cache will have 8 lines per set. When determining where to place a piece of memory that has just been read or written to, the memory address is split up into the tag, set, and offset going from most significant bit to least significant bit. If you have a 32-bit memory address with 64 sets and 64 byte lines, it will be split up as such:
tag: 00000000000000000000 | set: 000000 | offset: 000000
This means that every 4096 (0x1000) bytes, the same set will be used. To differentiate which line belongs to which address, the tag is checked against what is stored in the cache.

Once the cache is filled, if a new line needs to get added, it will evict one of the lines currently in that set. While there are multiple methods to determine when a line needs added and which line needs replaced, the CPU used in this paper uses write-back and Least Recently Used (LRU). The write-back cache strategy means that every time a write occurs, the data is written to L1 immediately. Once it gets evicted, it gets written to the next level of cache until it is written to memory and storage. This means every read that relies on the write only has to wait for L1 speed. To determine if the line gets evicted, the LRU strategy is used. As it sounds, this evicts the cache line that was read from or written to least recently.

\subsection{Prime+Probe}
Prime+Probe consists of three phases:
\noindent\begin{enumerate}[leftmargin=*]
    \item \textbf{Prime:} Fill cache sets with attacker data
    \item \textbf{Victim Execution:} Victim accesses memory
    \item \textbf{Probe:} Measure access time to detect evictions
\end{enumerate}

\noindent This exploits the time difference from accessing memory at different cache levels to understand the cache access patterns of different programs. That data can be used to determine which programs are running on the system or even what they are doing depending on how they handle memory access in different states.

\subsection{Vector Instructions}
Vector instructions or Single Instruction Multiple Data (SIMD) instructions operate on multiple data elements simultaneously. These often don't come with the standard Instruction set Architecture (ISA) of a chip and need to be added with extensions like MMX, SSE, AVX2, or AVX512 on Intel\textsuperscript{\tiny\textregistered}. As the SIMD acronym suggests, these instructions go beyond the normal data size of an ISA (such as 64 bits for x86\_64) and allow 1 instruction to operate on 128, 256, or even 512 bits at once.

The reason these instructions are being looked at for prime and probe is to evaluate the effect of evicting entire cache sets with one instruction. How does prefetching play a role? Will there be a difference in timing depending on the number of lines evicted? What does the decrease in timing overhead do?

While those benefits may be promising, not all CPUs support all vector instructions (especially the ones employed here). More CPUs are adopting AVX512, but it is still an enthusiast/professional focused market.

\section{Related Work}

% 1. Prime & Probe foundational work
Prime+Probe has been around for a long time. While the concept is simple, it has has to adapt to more and more complexities around cache optimization. Even with that, there have been multiple recent examples of side-channel attacks being used to great effect such as one from Gulmezoglu et al. that explored retrieving AES secrets across virtually isolated environments that share the same hardware\cite{7447807}\cite{10.1007/978-3-662-53140-2_18}. This takes advantage of the cloud's infrastructure at scale model where they focus on outfitting servers with large CPUs that they virtually split up to fit customer needs\cite{7363305}.

In addition to cloud, Gulmezoglu et al. also explored the shared model of mobile applications. They were able to detect running applications, opened websites, and streaming videos using Prime+Probe on the LLC\cite{10.1145/3321705.3329804}. While using the LLC is traditionally noisy and difficult to work with in Prime+Probe, it is still possible to work with them using various techniques\cite{7163050}. The technique used by Gulmezoglu et al. shows how Convolutional Neural Networks (CNN) can be used to interpret the often noisy timing data of Prime+Probe.

There are also a series of studies exploring Prime+Probe beyond the CPU cache level. Many levels of the compute stack have taken notice of the cache structure and have started to use it. From Linux file pages\cite{Kaur2021} to 

% 2. High-precision / observer-effect work
In addition to Prime+Probe, there are other similar cache timing techniques such as Flush+Reload\cite{184415}\cite{10.1007/978-3-319-21476-4_8}\cite{7447807} and Prime+Scope\cite{10.1145/3460120.3484816}. Flush+Reload is often seen as a less desirable version of Prime+Probe because it requires shared memory between the attacker and victim. On the other hand, Prime+Scope aims to improve two things from Prime+Probe. First, it aims to reduce the observer effect (how much the victim program is slowed down due to probing from the attacker). Secondly, it aims to reduce the time between each probe (increase timing resolution). This means that the program will identify the eviction of a cache set closer to when that set is actually evicted from the program. The initial Prime+Scope paper does this by only accessing one cache line in a set at a time. The is a place where vector instructions can offer a similar benefit as each line is accessed in parallel instead of in sequence. Vector instructions will, however, still have the same observer effect because each probe will evict the entire cache set.

% 3. Prefetcher-aware and microarchitecture-aware attacks
When trying to improve the efficacy of Prime+Probe, it is also important to take into account all of the cache, memory, and compute optimizations built-into the CPU. Zhang et al. Explores all the most common optimizations and speculative execution strategies used in modern CPUs\cite{10.1145/3645109}. These techniques like branch prediction, store-to-load forwarding, and memory disambiguation can all cause run-to-run variance and prevent typical cache usage during execution. This is why multiple runs and data aggregation is required during the attack. In addition to the aforementioned microarchitectural challenges, the prefetcher adds a uniquely challenging obstacle to timing memory access. Whang et al. explores these complications and proposes a solution using a technique to reverse engineer the prefetcher and replacement policy in order to construct a priming and probing sequence that prevents prediction\cite{10.1145/3316781.3317877}.

% 4. Vector/SIMD/cache interaction
In spite of searching, there appeared to be no articles about using vector instructions during either the prime or probe phase. The only article related to the influence of vector instructions on Prime+Probe attacks was a paper discussing identifying Deep Neural Networks with Prime+Probe. It discussed the unique cache behavior of a function built around vector instructions and how that could be leveraged to identify the different programming techniques behind the core models used in the study\cite{10.1145/3658644.3690241}. This presents a large gap for further research in the space of using vector instructions in the prime and/or probe operations.

% 5. Defenses and cache-randomization
For any system owner looking to prevent Prime+Probe attacks, there have been a few articles put out around defense and detection. As discussed already, the complexities in the design of modern CPUs act as a safe-guard/noise make to prevent simply using the naive approach. There has, however, been a breadth of research around techniques to circumvent these natural difficulties\cite{Kaur2021}. As for more proactive approaches, cache set randomization has been discussed as the primary defense as it cuts the technique off at the source\cite{236344}. This makes it so that behavior cannot be tracked to a set easily. On the other hand, neural networks are increasingly used to interpret data and may be able to associate run-to-run differences with each other. As for detection, SCADET has been offered as an option. This analyzes the cache access patterns of different Prime+Probe techniques to identify and stop them as they run\cite{10.1145/3240765.3240844}


\section{Threat Model}

This paper aims to capture the cache behavior of another program running on the same hardware. This will be done in two phases: initial analysis and attack. The initial analysis phase will allow the attacker more control as it is assumed the attacker is using their own hardware to collect data and understand patterns. These patterns are later applied in the attack phase where the attacker will have more limited access to the system as described below.

\textbf{CPU Requirements:} It is assumed that the victim is using a CPU with the AVX512 ISA extension. While the option to use AVX2 instructions is briefly covered, the experimentation and data was carried out using instructions from AVX512. In addition to that, results will be specific to a specific CPU and even microcode update, so both the analysis and attack phases will be required to use the same CPU for the most accurate results. 

\textbf{Black-box Remote Access:} The aim for this attack is to parse memory access times for a remotely executed process where the other program running or lack thereof is not known to the attacker. To understand the patterns that appear in data, however, initial analysis is done understanding what process is running and influencing the Prime+Probe results. Any interpretation of that data can be influenced by the initial analysis, but it should not require any knowledge of the system aside from the timings.

\textbf{Unprivileged Execution:} This paper assumes that during the attack the program will run with normal user permissions. That prevents the attacker from using system-level interfaces for isolation or disabling protections. For the initial data collection and analysis, full access to the system is expected. This allows the attacker to turn off the scheduler and other processes that may add noise to measurements.

\textbf{Shared hardware:} Due to the nature of L1 caches, it is required that attacker shares a core with with the victim it would like to analyze for L1 timing analysis. Part of data analysis should be that the attacker will be able to determine if the victim function is running at all. As shown in other papers, there are techniques for analyzing LLC activity \cite{7163050}. If this is the desired use, then the two processes only need to be on the same CPU. In addition to that, Intel\textsuperscript{\tiny\textregistered}'s IA Cores introduce E Cores where the MLC is shared. This would allow execution on any E Core to probe the MLC on another E Core\cite{ia-cores}.

\subsubsection{Scalar Prime+Probe}
The scalar Prime+Probe program this project used as a baseline was created by Debopriya Roy Dipta. It uses a pointer chase technique for memory access and uses a function that evicts one cache line to evaluate timing differences. This produces a pronounced difference in the experimental timing compared to the baseline.

\subsubsection{Vectorized Prime+Probe}
During the project, multiple PoCs were developed:
\begin{itemize}[leftmargin=*]
    \item avx\_cache\_fill\_with\_time.asm
    \begin{itemize}[leftmargin=*]
        \item Consistently calls and times \texttt{vpgatherqq} on 8 addresses 0x1000 bytes apart while logging anomalies (> 30 cycles)
    \end{itemize}
    \item avx\_cache\_fill\_with\_time\_avx2.asm
    \begin{itemize}[leftmargin=*]
        \item Modification of \emph{avx\_cache\_fill\_with\_time.asm} to use AVX2 \texttt{vpgatherdd}
    \end{itemize}
    \item ping\_memory.c
    \begin{itemize}[leftmargin=*]
        \item Spins off a process that accesses memory every set time while running \emph{avx\_cache\_fill\_with\_time.asm}
    \end{itemize}
    \item Prime-Probe.c
    \begin{itemize}[leftmargin=*]
        \item Modification of Dipta's scalar Prime+Probe program to use vector instructions and enable a variety of tests
    \end{itemize}
\end{itemize}

As mentioned in the description of some PoCs, the \texttt{vpgather} family of instructions was chosen to perform simultaneous memory accesses. \texttt{vpgather} takes in a base memory address, list of offsets, scale (1, 2, 4, or 8), mask, and list of fallback values. Every \texttt{vpgather} instruction is followed by two letters (i.e. \texttt{vpgatherdq}). The first letter represents the size of each integer packed into the offsets argument. The second letter marks the size of data to read from memory. A d is for 32 bits while a q means 64-bits. The aforementioned \texttt{vpgatherdq} instruction reads a series of 32-bit integers from the offsets vector and reads a 64-bit integer from the address it resolves to. The instruction takes that information and follows this logic flow according to Intel\textsuperscript{\tiny\textregistered}\cite{intrinsics}

\begin{lstlisting}[language=Python]
for j = 0 to register_len/data_size:
    i = j*data_size
    m = j*data_size
    if mask[j]
        addr = base_addr + offsets[m:m+(data_size-1)] * ZeroExtend64(scale) * 8
        dst[i:i+(data_size-1)] = MEM[addr:addr+(data_size-1)]
    else:
        dst[i:i+(data_size-1)] = fallback[i:i+(data_size-1)]
\end{lstlisting}

For the purposes of Prime+Probe on the chip that was used, \texttt{vpgatherqq} (512) and \texttt{vpgatherdd} (512/256) work best. \texttt{vpgatherqq} uses 8 64-bit offsets to read 8 64-bit integers from memory when 512-bit registers are used. This fills each cache line in L1D because it is 8-way associative (has 8 lines per set). However, not all common CPUs have support for AVX512. This is where \texttt{vpgatherdd} with 256-bit registers in AVX2 can be useful. It reads 8 32-bit numbers from memory and fills most L1D caches. With 512-bit registers, it reads 16 32-bit integers and fills the L2 cache. This could be useful for evaluating the L3 cache as well as evaluating the influence of instructions based on the unified nature of the L2 cache.

\subsection{Tuned Variables}\label{sec:tuned-variables}
To explore the different ways vector instructions affect the Prime+Probe attack, there were multiple knobs and dials turned between runs. This changes how impactful different underlying CPU optimizations were to the timings, and while several different variables were considered and trialed, the most impactful/interesting ones were found to be:
\begin{itemize}[leftmargin=*]
    \item Parallel vs. serial timing
    \item Fencing vs. pipelining timings
    \item Timing window
    \item Payload
\end{itemize}

\subsubsection{Parallel vs. Serial Timing}
The initial Prime+Probe program would run a baseline prime -\> probe with a following prime -\> victim -\> probe. Because the victim function simply accessed a line in the set multiple times, this ensured it was finished before the probe timing was done. For a more complex program, however, this combines all evictions into one measurement and doesn't give the granularity or insight desired.

A parallel version starts by doing multiple rounds of priming before splitting the program into two processes or threads where one continuously probes the memory and another runs the victim function/program. This allows the attacker to watch the cache state change in real time and evaluate cache access patterns. An example of where this can be useful is determining if differences in timing with the victim function are from outlier/spikes or a chronic increase in the access timings.

\subsubsection{Fencing vs. Pipelining Timings}
Traditional Prime+Probe techniques say to do primes and probes the following way:
\begin{lstlisting}[language={[x86masm]Assembler}, caption=Fenced rdtsc example]
mfence
lfence
rdtsc
lfence
; access memory
mfence
lfence
rdtsc
lfence
\end{lstlisting}

\texttt{mfence} will ensure that all memory stores are globally visible while \texttt{lfence} ensures that all memory loads are globally visible. Ideally, this ensures that the only memory loads being measured are from the instruction itself, and that any stores/loads that would evict one of the cache lines would already be committed to memory.

During testing, however, this was providing cycle times far above the expected latency\footnote{Latency is the number of cycles it should take for the instruction to make it from one end of the pipeline to the other}. Initially this was suspected to be because of compiler optimization issues, but converting the probe function to assembly only reduced the baseline cycle measurements from \textasciitilde130 to \textasciitilde120 in spite of notable differences in the assembly itself.

LFENCE
NOP
RDTSC
SHL        RDX ,0x20
OR         RAX ,RDX
MOV        qword ptr [RSP  + local_198 ],RAX

MFENCE
NOP
LFENCE
NOP
RDTSC
SHL        RDX ,0x20

While the custom assembly still has overhead with instructions between the timings, none of the instructions access memory, and all of them are simple and efficient. The C version, on the other hand, Has multiple instructions that pull data from memory. While each of these instructions have a low latency (\textasciitilde1 cycle), the access time is expected to be much larger due to the time it takes to reference even L1 cache. Not being able to see as large of a gap is evidence that there may be microarchitectural requirements for the instruction that lines up similarly to the instructions from the C version after all the instructions have been pipelined. For this reason, both the fenced rdtsc (fencing) and unfenced rdtsc (pipelining) were evaluated to understand how the processor's predictions and pipelining impacts the readings.

\subsubsection{Timing Window}
The window is a technique sometimes used with parallel Prime+Probe timing to give the program room to breathe and evict more cache sets to get readings from L2 and L3 caches. This is done by adding a nanosleep timer between probes.

\section{Analysis}\label{sec:analysis}
Each of the variables except the payload had a significant impact on the data. While the end-goal is to identify programs through cache timings, the findings from this project act as a jumping point for further research that uses techniques to reduce noise. This means evaluating the usefulness and impact of each variable and what effects it had on the data independently. In addition, it's worth noting the patterns identified across the datasets and what that may indicate for future data as covered in \ref{sec:patterns}

\subsection{Effectiveness of Parallel Probing}
While the Serial measurements did provide evidence that vector instructions can detect evicted sets in the cache, it is clear that parallel probing is the way forward. Parallel probing showed various patterns that enabled additional insights into the possible patterns of cache access and impacts of CPU procedures on the average times. That is the reason most of the provided experiments involved the parallel probing technique. Patterns identified in the timing data directed further experimentation where theories around how those patterns may change could be confirmed. Patterns that were identified will be expanded upon in other tests.

\subsection{Pipelining Impact on Instruction Timing}
To start, the standard timing with proper fencing around \texttt{rdtsc} produces results around the 110-140 cycle range. This is far from the the predicted latency of 26 cycles for \texttt{vpgatherqq}\cite{intrinsics}. On the other hand, letting the timing and gather get pipelined together produces values around either 25 or 60. While this appears to be more accurate or closer to timing the exact instruction timing, further testing showed that pipelining also made patterns that appeared with properly fenced timing disappear. This means that focusing on the proper timing is likely the most useful technique, but more evaluation is needed on what microcode operations happen in the background to slow down the fenced instruction.

\subsection{Window}
The window technique appears to have provided the expected results: an increase overall in timings and larger jumps outside of outliers. It did also increase the baseline measurements by roughly 50 cycles in each parallel, fenced run. This was unexpected, but the relative measurements from that baseline kept the same pattern seen across the other parallel, fenced runs discussed below. Outside of that, increasing the window also appeared to increase the number of measurements that ended up at those higher levels as expected.

An important note on the window time itself, the total cycle time for both the 1ns and 100ns windows was around 100,000,000 cycles (up from 1,000,000 without it). With a 2-3 GHz processor, it is expected that only 2-3 cycles passes per nanosecond. This should add an extra 2-3 cycles per measurement for the 1ns window (not including interupt overhead) and 200-300 cycles per measurement with the 100ns window. With 1,000 measurements per run, this should not add an extra 99,000,000 cycles or 99,000 cycles per measurement. There must have been some process that takes advantage of the sleep and holds the interrupt for some time. Larger windows should be tested to determine when they take effect.

\subsection{Patterns Across Experiments}\label{sec:patterns}
While the series experiments were able to show that vector instructions had promise and some use, there weren't any additional patterns in the data, and any apparent patterns across sets did not stand up to a second run of the program. With that in mind, many other variables tended to obscure or modify the underlying patterns in a predictable way already covered above. This section is focusing on the patterns identified in the parallel, fenced runs.

To start, there are a few key outliers. The first outliers are the first two measurements. These tend to be 3.5x and 1.5x the typical cycle time in the data. This is expected to be the prefetcher warming up to get the data. There is a necessary setup period for the experiment after the baseline is taken, and this likely clears the training the baseline does. The second class of outliers happens roughly every 175,000 cycles, and it appears to be 1.5x the baseline. This is likely related to the scheduler as there are other clear behavior changes around these marks. Because the difference is also close to the level of the second sample, it is hard to tell if the cache or the prefetcher is causing the difference. The final class of "outlier" is very similar to the second, but the cycle difference is much smaller at 1.1x-1.2x. This means it often hides among the other readings, but it has similar behavior and implications to the second outlier.

The rest of the data appeared to coalesce around 3 distinct levels that were each roughly 10 cycles apart. There was the baseline, and there were the two levels that would always occur in parallel. The baseline is likely some form of prefetch/prediction cache. On the other hand, the parallel lines likely come from a program reading from memory and processing between reads. This gives time for the Prime+Probe program to re-fill and recheck the timing before the next read. The inconsistency forces the program to read from L1D instead of a pre-prepared cache and slows the read slightly. This theory stems from the fact that the parallel lines always start and end at timing spikes such as the second and third outlier.

Finally, it's worth noting that there was a consistent lack of notable data in the sets right below 16 and 32 with set 0 having the most consistent show of patterns. This is likely because the addressing for the L1D cache takes fewer bytes then are affected by ASLR, so aligned, larger data structures will consistently use lower sets. For example, a program allocates 1KiB of data aligned to 1KiB. That data either starts in set 0, 16, 32, or 48, and any unused data would likely be around set 15, 31, 47, or 63. This was most noticeable in the 100ns window.

\section{Limitations}
\begin{itemize}[leftmargin=*]
    \item Results may be hardware-specific
    \item Limited instruction sets evaluated
    \item Noise in timing measurements
        \item Scheduler
        \item Program overhead
        \item Cache management
    \item CPU predictions
        \item Prefetching
        \item Branch prediction
\end{itemize}
As with all Prime+Probe attacks, every CPU acts differently, and even the same CPU with different microcode can behave differently. This means that these results are specific to the Intel\textsuperscript{\tiny\textregistered} Xeon\textsuperscript{\tiny\textregistered} Gold 5218 CPU @ 2.30GHz mentioned above and may not replicate to other AVX512 enabled chips. On top of that, this exploration was focused on the AVX512 and AVX2 ISA extensions for x86\_64 processors. There are multiple other vector instructions that to vectorized memory read such as ARMs \texttt{LD1SB} or RISC-Vs \texttt{vluxei}.

The most apparent source of noise was the scheduler. It was clear that cache lines were getting evicted even without a program expected to be running on the same core. While this did show that the program can identify different states in the cache, it trampled the noise from the payload and made it difficult to understand what effect known access patterns would have. This can be turned off using the \texttt{isolcpus} flag at boot to prevent the scheduler from using certain cores.

As for the data itself, there was clearly a lot of noise due to the processor's techniques used to speed up instructions and memory access. Prefetching appeared to be reducing the timing floor and typical access time. During other trials, branch prediction was changing the average cycle time for subsequent calls to the Prime+Probe function. Some of these optimizations like the prefetcher can be turned off in hardware, but this should be done with caution and the understanding that it will likely cause the system to slow.

On top of the CPUs built-in behavior, an inherent part of collecting data in a program is that there needs to be some from of I/O. That can be to STDOUT, a file, or a location in memory, but the tracking need to use memory, and that can add noise and overhead. Further evaluation is needed for the best data collection technique.

\section{Conclusion}
While vector instructions sound like a promising direction for Prime+Probe attacks, there are many limitations. The use of one instruction makes it more prone to CPU optimizations, and gathering all of the memory at once can obscure individual set evictions. Even with this, there is still promise due to the speed and efficiency of each probe. This provides fewer cycles between measurements and more possible insight into how a program behaves.

Future work should focus on reducing noise by turning off hardware optimizations and getting a better understanding of cache access behavior through more granular performance monitors.
